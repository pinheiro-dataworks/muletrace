# Data card

**Everything in this project is synthetic.** MuleTrace uses IBM AMLworld, a fully simulated
financial world, plus a seeded Pix layer generated by this repository. No real person, account,
bank or transaction appears anywhere. Counts below are generated by code
([`docs/generated/data_profile.yaml`](generated/data_profile.yaml) and
[`docs/generated/pix_layer_calibration.yaml`](generated/pix_layer_calibration.yaml)); none is
typed by hand.

## 1. Origin

| | |
|---|---|
| Dataset | IBM Transactions for Anti Money Laundering (AML), known as AMLworld |
| Publisher | IBM Research (Kaggle owner: Erik Altman) |
| Source | Kaggle `ealtman2019/ibm-transactions-for-anti-money-laundering-aml`, version 8 (updated 2025-07-08) |
| Paper | Altman et al., *Realistic Synthetic Financial Transactions for Anti-Money Laundering Models*, arXiv:2306.16424; the Kaggle page announces it as appearing at NeurIPS 2023 |
| Licence | Community Data License Agreement – Sharing, Version 1.0 (CDLA-Sharing-1.0), confirmed on the Kaggle dataset metadata; full text in [`data/LICENSES/CDLA-Sharing-1.0.txt`](../data/LICENSES/CDLA-Sharing-1.0.txt) |
| Files used | `HI-Small_*` (higher illicit ratio) and `LI-Small_*` (lower illicit ratio): transactions, accounts and patterns |
| Integrity | Size and SHA-256 of every file in [`data/MANIFEST.yaml`](../data/MANIFEST.yaml); `muletrace data verify` checks them |

**How it was made.** An agent-based simulator models individuals, companies and banks making
everyday payments and inserts laundering that follows known typologies. The laundering tag is
transitive: funds derived from an illicit transfer stay labelled through later hops, including
when mixed with legitimate funds (paper, Section 3.4). Because the world is simulated, every
laundering transaction is labelled, which real bank data can never offer.

## 2. What the files contain

| | HI-Small | LI-Small |
|---|---:|---:|
| Transactions | 5,078,345 | 6,924,049 |
| Laundering transactions | 5,177 | 3,565 |
| One laundering transaction per | 981 | 1,942 |
| Accounts in the accounts file | 518,581 | 712,688 |
| Accounts that appear in transactions | 515,088 | 705,907 |
| Self-transfers (same account on both sides) | 591,212 | 804,477 |
| Mule accounts (received ≥ 1 laundering transfer, self-transfers excluded) | 3,984 | 3,303 |
| Laundering attempts in the patterns file | 370 | 117 |
| Pattern transactions, all linked to a `tx_id` | 3,209 | 1,023 |
| Share of laundering covered by a pattern | 62.0% | 28.7% |

**Time span.** The primary period is 1–10 September 2022. Both files have a short tail up to
18 September (HI-Small) and 17 September (LI-Small). The Kaggle description says the tail
transactions are all laundering; in the downloaded version, **655 of the 1,108** HI-Small tail
transactions and **134 of the 223** LI-Small tail transactions are labelled laundering. MuleTrace
reports this as found and keeps the tail out of the scoring dates (see the target definition in
`configs/labels.yaml` and the backtest design in `docs/eval_report.md`).

**Typologies** (attempts in HI-Small / LI-Small): bipartite 49 / 16, cycle 54 / 12, fan-in
40 / 12, fan-out 48 / 19, gather-scatter 51 / 12, random 41 / 15, scatter-gather 44 / 13,
stack 43 / 18. Not all laundering follows a pattern: the rest is labelled but has no typology.

**Payment formats.** ACH carries most laundering (4,483 of 5,177 in HI-Small; 2,611 of 3,565 in
LI-Small). Wire and Reinvestment carry none in either file.

**Entity types** come from the entity name in the accounts file (`Corporation #33520` →
`Corporation`). HI-Small has 172,351 corporations, 189,683 partnerships, 149,048 sole
proprietorships, 740 individuals, 6,692 `Country` and 67 `Direct` entities; LI-Small has no
`Country` or `Direct` entities. Accounts that appear only in transactions get `Unknown`.

## 3. What MuleTrace changes during ingestion

Nothing in the source rows is altered. Ingestion only adds structure
([ADR-004](adr/004-identifiers-and-data-layout.md), [ADR-005](adr/005-exchange-rates-from-the-data.md)):

- `tx_id`: the zero-based data-row number in the source CSV.
- `account_id`: a compact identifier for `(bank_id, account_number)`; bank codes are normalised
  from zero-padded strings to integers so both files join (100% of transaction accounts match).
- `amount_paid_usd`: the paid amount converted with exchange rates **inferred from the data's own
  cross-currency transfers** (median of `amount_received / amount_paid`). Fiat rates are
  effectively constant (relative interquartile range below 1e-5); Bitcoin varies (about 5%).
- `is_self_transfer`, enums for currencies, formats and entity types.
- Pattern rows are linked to `tx_id` on every field plus their rank among identical copies; the
  source has 9 (HI-Small) and 8 (LI-Small) byte-identical transactions.

## 4. The Pix layer (simulated, version 0.1.0, seed 20261108)

AMLworld has no Pix keys, no dispute mechanism and no Brazilian context. A seeded simulator
(`src/muletrace/data/pix_layer_simulator.py`, configured in `configs/simulator.yaml`) adds them
next to the AMLworld rows, never inside them. Its tables never contain the laundering label.

| Table | Content |
|---|---|
| `pix_transfers` | ACH and Wire transfers between different accounts, re-labelled as instant transfers, with a BRL amount, the night-time limit check and a synthetic description |
| `pix_keys` | One synthetic key per account (opaque token; e-mail keys use `example.invalid`) and its registration time |
| `pix_dict_markings` | A DICT-style fraud marking for every confirmed mule, at confirmation time. DICT is the Pix directory of keys and accounts where institutions mark confirmed fraudsters |
| `pix_disputes` | MED-style disputes: accepted ones on transfers that bring laundered money into a mule account, rejected ones on ordinary transfers |

### Calibration to public figures

The simulator is calibrated only to public aggregates, frozen in
[`configs/calibration/bcb_public_figures.yaml`](../configs/calibration/bcb_public_figures.yaml)
by `scripts/fetch_bcb_calibration.py` from the Banco Central do Brasil open-data service
(`Pix_DadosAbertos`), accessed on 2026-11-09 (UTC).

| Target | Public figure | Source and period | HI-Small achieved | LI-Small achieved |
|---|---:|---|---:|---:|
| Accepted disputes per 100,000 instant transfers | 4.31 | BCB MED statistics, median of Oct 2025 – Sep 2026 | 4.28 | 4.31 |
| Share of disputes rejected | 90.85% | BCB MED statistics, Oct 2025 – Sep 2026 | 90.85% | 90.85% |
| Average accepted ticket | R$ 2,265.03 | BCB MED statistics, Oct 2025 – Sep 2026 | R$ 4,002,140.67 (median R$ 22,540.57) | R$ 61,161.99 (median R$ 21,417.57) |
| Key-type mix, individuals (random / phone / tax id / email) | 52.66% / 16.89% / 15.95% / 14.50% | BCB stock of Pix keys, 31 Oct 2026 | 52.55% / 16.89% / 15.92% / 14.64% | 52.56% / 16.91% / 15.94% / 14.60% |
| Key-type mix, companies (random / tax id / email / phone) | 51.03% / 31.66% / 10.35% / 6.96% | BCB stock of Pix keys, 31 Oct 2026 | 50.95% / 31.80% / 10.36% / 6.89% | 50.98% / 31.72% / 10.38% / 6.93% |

**The ticket does not match, on purpose.** Amounts are AMLworld's own, converted to reals; the
simulator does not rescale them, because that would break the link between a cited transaction
and its source row. AMLworld laundering transfers are far larger than Brazilian scam transfers,
and a few very large ones dominate the mean. Any monetary figure in this project ("value
detected") is therefore synthetic and must not be read as a Brazilian amount.

### Other sourced parameter

- **Night-time limit.** R$ 1,000 per transfer between individuals from 20:00 to 06:00, the
  default described in the BCB *Relatório de Gestão do Pix* (2023). It is applied as a check
  (`exceeds_night_limit`), not by blocking transfers, because AMLworld's transfers already
  happened.

### Assumptions (not sourced)

| Parameter | Value | Why |
|---|---|---|
| Formats re-labelled as instant transfers | ACH, Wire | Account-to-account electronic transfers are the closest AMLworld analogue to Pix |
| Entity types treated as natural persons | Individual, Sole Proprietorship | Sole proprietorships approximate Brazilian MEI accounts; AMLworld has very few individuals |
| Key registration time | Uniform over the year before the account's first transfer | Keeps key age independent of the mule label, so it carries no injected signal |
| Mule confirmation delay | 24 hours after the first illicit inflow | See assumption A3 in [business_case.md](business_case.md) |
| Dispute filing delay | Uniform 1–72 hours after the transfer | No public figure found |
| Scam scenarios and transfer descriptions | Short English templates written for this project | They exist to give the copilot a free-text field to be attacked through (prompt injection tests) |

MED 2.0 tracing parameters (`MinTransactionAmount`, `MaxTransactions`, `HopWindow`, `MaxHops`) are
named in the BCB presentation *Aprimoramentos no Mecanismo Especial de Devolução – "MED 2.0"*
(Circuito Pix, 14 October 2025), but their values are not published there. The tracer keeps them
configurable and labels its defaults as assumptions.

## 5. Limitations of synthetic AML data

- **Labels are perfect and complete.** Real labels are partial, late and biased towards cases
  that were investigated. MuleTrace models lateness with a confirmation delay and measures its
  effect, but cannot model the bias of real investigation queues.
- **Ten days of primary activity.** Horizons and windows are hours and days. Nothing here says
  how a model ages over months.
- **"Mule" is a proxy.** Any account that receives laundered money counts, including final
  recipients where funds are spent. A real mule definition would also require onward movement.
- **Amounts and currencies are AMLworld's.** BRL values come from the simulator's own rates and
  do not resemble Brazilian transfer sizes.
- **The Pix layer is thin.** Keys, markings and disputes are generated with simple rules and
  calibrated to a few aggregates. They support the tracer, the copilot and the demo; the model
  does not use any Pix-layer field as a feature (so its results do not depend on choices made in
  the simulator).
- **No personal data.** There is none to protect in the data itself; LGPD and GDPR do not apply to
  the dataset. They do apply to how the same design would be used on real data, which is covered
  in `docs/threat_model.md`.
